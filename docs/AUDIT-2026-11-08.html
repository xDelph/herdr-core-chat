Audit backend, front et API herdr-core, puis feuille de route

L'analyse a été faite en lecture seule par trois auditeurs (backend Rust, PWA, écarts avec l'API herdr-core). Chacun a lu le code et relancé les portes qualité. Les constats les plus graves ont ensuite été relus une seconde fois dans le code avant d'entrer dans ce document.

Synthèse

La base est saine et bien écrite. Les invariants sont documentés là où ils servent, les portes qualité sont vertes, et l'isolation par pane, les époques du suivi de session, les curseurs, le confinement cap-std et la file de 900 ms tiennent. Les défauts trouvés se concentrent sur trois axes :

  1. Les actions interactives ne vérifient pas que leur cible est encore celle que l'utilisateur a vue. C'est le cas d'une réponse à une question, d'un prompt envoyé pendant une question, et d'un changement de modèle. Côté front, un résultat inconnu est présenté comme un échec, ce qui pousse à refaire l'action en double.
  2. La vérité se dégrade entre herdr-core et l'écran.
    • Le champ turn est lu puis jeté, si bien que des fins de tour sont perdues.
    • Le data.kind se fond dans des 502 génériques, et hint/cause ne sont jamais lus par le web.
    • Le statut error est affiché comme « waiting for input ».
    • exit_code et reason sont ignorés.
  3. Une grande partie de l'API reste inexploitée. events.subscribe, records (les sous-agents Claude en direct, vérifié sur ta machine), status.msg/kind/progress, terminal.put (photos depuis le téléphone), terminal.get/wait, le label where et herdr.pinned n'apportent encore rien à l'app.
Légende des preuves. relu = relu une seconde fois dans le code pendant la synthèse · vérifié = code lu et chemin tracé par un auditeur · plausible = effet déduit, sans exécution. Les chemins sont relatifs à la racine du dépôt.

Feuille de route proposée

Lot 0 — Corrections rapides (moins d'une heure chacune, sans risque)

  • Cache des assets : crates/http-api/src/assets.rs:58 découpe sur le dernier -, donc index-Dz3mv-FR.js n'est pas reconnu comme immuable. Prendre les 8 caractères avant l'extension et vérifier le - qui les précède. relu
  • Flux SSE : handlers/events.rs:93 doit prendre frontiere = rattrapage.reprendre_de et non journal.dernier_id(), relu après l'abonnement. relu
  • Résolution codex : refuser l'ambiguïté (LIMIT 2, comme opencode) au lieu de order by updated_at desc limit 1 (sessions/src/resolver.rs:402).
  • Front, petites corrections :
    • la saisie libre est effacée avant le résultat (chat/Question.tsx:124) ;
    • le projet de la feuille de lancement reste figé à vide (feuilles/Lancement.tsx:93) ;
    • try manquant dans presence.ts:51 ;
    • stats.html est servi publiquement : le sortir de dist ;
    • ajouter le build à verify (F04, toujours ouvert).
  • Cibles tactiles de 44 px : Cancel, Retry, Edit et Dismiss des envois ne font que 22 px (conversation.css:290).
  • Afficher status.msg en sous-titre des lignes « working ». La donnée est déjà dans terminal.list.

Lot 1 — Ne jamais agir sur la mauvaise cible (prioritaire)

  • Une empreinte de question et d'invite sur chaque action interactive (réponse, confiance, modèle), avec un refus 409 si l'écran a changé.
  • Un prompt reçu sur blocked/question est refusé, ou dirigé vers « Type something » ; il ne doit plus partir en force + Entrée.
  • Le changement de modèle n'est accepté que sur idle ou done, d'après une observation fraîche.
  • Un envoi à un agent working s'affiche « queued » et non « confirmed ».
  • Côté front :
    • « Launch outcome unknown » au lieu de « Launch failed » ;
    • un 5xx sur une réponse ou un changement de modèle devient « sent, unconfirmed » et non « rejected » ;
    • confirmation en deux temps pour les choix à conséquence dans la boîte de réception ;
    • clé Idempotency-Key sur tous les POST.

Lot 2 — Rendre fidèlement ce que dit herdr-core

  • Faire de turn une donnée de premier rang : dans AgentView, dans la signature de la veille, pour la déduplication des push et pour la confirmation d'envoi.
  • Traduire chaque data.kind en nature de domaine, puis en statut HTTP et code stable dans ApiErrorResponse. Le front mappe par code et non plus par regex.
  • error, finished, exit_code, reason et blocked.kind entrent dans le contrat, avec des cartes dédiées (voir les maquettes).
  • Gardes RAII sur le cache de snapshot, la santé et l'admission (un panic ne doit plus bloquer le démon), plus un délai global.
  • Exposer l'état de la veille dans /health ; ajouter un battement SSE nommé et la reconnexion du flux global.
  • Arrêt : accepter aussi blocked, error et unknown, et exposer outcome.

Lot 3 — Performance

  • Côté backend :
    • écran mis en cache par (pane, turn, status_ms) ;
    • permis de lecture globaux ;
    • cache de résolution de session ;
    • index incrémental par session, pour éviter les remontées de 2 à 32 Mio sur le chemin des requêtes.
  • Côté front :
    • afficher l'overview (3,5 ms) avant /api/conversations (5 à 6 s à froid) ;
    • ne pas refaire le JSON.parse de la file d'attente à chaque delta ;
    • sélecteurs mémoïsés ;
    • fenêtre glissante sur le fil.

Lot 4 — Nouvelles capacités issues de l'API (à prouver d'abord sur un core isolé)

  • events.subscribe à la place de l'interrogation toutes les 2 s.
  • Sous-agents en direct grâce à records.
  • Pièces jointes et photos grâce à terminal.put.
  • Fin d'agent expliquée.
  • Épingles partagées.
  • Boîte d'envoi et centre de santé.
  • Plus tard : vue terminal en direct (terminal.attach {observe:true}) et machines distantes.

Messages d'erreur : de herdr-core à l'écran

Le data.kind d'herdr-core survit jusqu'au port (PortError::Upstream{code}), puis disparaît. Côté web, hint et cause ne sont jamais lus, et les erreurs sont reconnues par regex sur des phrases, dont une ne correspond plus à rien.

not_found, finished502 « answer failed / Ctrl+C refused / model change failed »404 / 410 · « Agent is gone » / « Agent exited (code 1, killed) »
blockedMessage « waiting for a permission answer », même sans kind409 + kind (permission / question / auth)
status_mismatchJamais produit (aucun if envoyé)409 « Agent started working — sent as queued? »
unavailable, needs_update, unsupported_generation502 générique ; /health en 503 sans cause503 avec la cause, visible dans /health et dans le centre de santé

Arbres de décision : branches manquantes

DécisionBranches non traitées ou incohérentes
Envoi d'un prompt
  • working → « confirmed » sans preuve ;
  • question → collage forcé + Entrée ;
  • blocked sans kind → message « permission » faux ;
  • terminal absent ou fini → 502 ;
  • un doublon légitime (« yes » deux fois en 60 s) est supprimé même si le tour a avancé (D007.2, levable grâce à turn).
Interruption
  • blocked, error et unknown ne sont pas interruptibles ;
  • les 4 outcome sont fondus en « sent » ;
  • un délai est rendu « refused » ;
  • côté front, pas de suivi « stopped » confirmé.
Question
  • Pas d'empreinte ;
  • branche sans curseur (opencode) : saisie libre vide non refusée, texte tapé hors saisie libre ;
  • flèches (pi) : texte ignoré ;
  • pas de contrôle blocked avant de répondre.
Confiance
  • Relecture immédiate, donc souvent « transmise » ;
  • snapshot en échec → « agent gone » ou « no key sequence », deux causes fausses.
Résolution de session
  • Une erreur passagère devient « sans fil » ou gone ;
  • codex devine le fil ;
  • JSONL pas encore créé → gone ;
  • pi, devin et cursor n'ont pas de cause ;
  • côté front, un seul texte « sans fil » pour 3 causes différentes.
Notifications
  • Pas de turn ;
  • working → unknown = « finished » ;
  • error → disparu : rien ;
  • le tag waiting-<pane> n'est pas remplacé par done-<pane> ;
  • blocked.kind non distingué (« Permission needed », « Question », « Sign-in needed ») ;
  • l'apparition d'un agent après un parc vide n'est pas annoncée.
Lancement
  • Course sur le nom ;
  • 20 s contre 125 s, puis kill ;
  • Started déclaré dès que le PID change ;
  • délai d'envoi = Failed ;
  • LaunchFailed{phase, paneId} est déclaré dans le contrat mais jamais émis ;
  • côté front, issue inconnue = échec, étapes invisibles (B08).
Boîte de réception
  • error rendu comme une attente ;
  • finished et code de sortie impossibles à représenter ;
  • auth rendu comme une attente générique ;
  • démarrage à froid : squelette pendant 5 à 6 s alors que l'overview est prêt.
Conversation
  • blocked pendant que conversations est en échec : pas de dock, et une aide trompeuse ;
  • error : pastille seule, composeur ouvert ;
  • erreur sans entrées : pas de Retry.

Compatibilité.
  • Fixer une version minimale (0.1.19 ?) et contrôler features au démarrage. On ne sait pas si un core plus ancien rejette un paramètre inconnu ou l'ignore : c'est décisif avant d'envoyer size ou display.
  • Le format de herdr.seen, herdr.pinned, where et du doc herdr-app appartient à Herdr.app (0.1.14 est déjà annoncée) : fixture versionnée, et jamais de doc.set sur herdr-app.
  • Les adresses machine/t7 doivent passer dans PaneId et dans les URL.

Maquettes

Les maquettes sont en 390×844, avec les jetons de tokens.css (la couleur porte l'état, le reste est à l'encre). Le texte de l'interface est en anglais (AGENTS §1.8), et le thème sombre suit celui du système. Chaque écran n'utilise que des données qui existent déjà côté herdr-core ou dans les sessions.

Documentation devenue fausse

  • L'en-tête de docs/PROTOCOL.md indique 0.1.17 / 0.1.12. Il manque terminal.get, terminal.wait, templates.list, machine.*, file.*, les nouveaux params de run, send et read, et les erreurs invalid_template, unreachable, incompatible… ; timeout a disparu du schéma.
  • notifications/src/payload.rs dit « Herdr rend pane.exited sans code ni raison » : c'était vrai pour 0.9.3, c'est faux pour herdr-core.
  • docs/IDEAS.md §2/§6 (« pas de statut error », « sous-agents sans source ») et RELEASE_BACKLOG (« pas d'upload ») sont contredits par status.error, records et terminal.put.
  • La fixture de test hello renvoie encore "0.1.17" (crates/herdr-core-client/tests/unit/transport.rs:16).

Le schéma OpenRPC complet de 0.1.19 et le relevé hc get des 24 terminaux sont dans le scratchpad de la session : schema.json et gets.jsonl.
